# Production audit

## Existing application

- No Dockerfiles, Compose file, reverse proxy, container health checks, or production startup scripts existed before this package.
- Django already separated development and production settings and used PostgreSQL through `DATABASE_URL`.
- Authentication uses host-only HttpOnly JWT cookies plus a readable CSRF cookie. The production package keeps one HTTPS origin, secure cookies, `SameSite=Lax`, explicit trusted origins, and proxy-aware HTTPS handling.
- Clinical documents and photographs use `PrivateMediaStorage` under `PRIVATE_MEDIA_ROOT`; they are never served as public static assets. The production volume is mounted only into Django, the reminder worker, and the read-only backup worker.
- PDF generation is entirely local through ReportLab, Pillow, bundled Vera fonts, and the local clinic logo.
- Operational reminders are generated by the existing `generate_reminders` management command. A dedicated scheduler container runs it every five minutes. No Celery broker exists.
- Redis is not used by current functionality, so no Redis service is added. Adding an unused data service would increase maintenance and attack surface.
- Application logs previously relied on defaults. Production now writes timestamped Django/Gunicorn logs to stdout, and every container has bounded JSON log rotation.
- The frontend's only remote build dependency was `next/font/google`. Plus Jakarta Sans is now bundled locally under its OFL license. No runtime CDN, remote image host, OAuth provider, telemetry dependency, or license check was found.
- Next.js telemetry is disabled in build and runtime containers.

## Production design

- Caddy 2.10.2 terminates HTTPS with its offline internal CA and is the only service publishing host ports.
- Next.js 16 uses standalone output on Node 22.20.0.
- Django 5.2 runs under Gunicorn 23 on Python 3.13.9 with WhiteNoise for collected static assets.
- PostgreSQL 16.10 is private to the container network and uses a persistent named volume.
- The web application logs in with a non-superuser, non-CREATEDB PostgreSQL role. The PostgreSQL administrative role is available only to the database and guarded backup/restore services.
- Containers have restart policies, health checks, resource ceilings, bounded logs, and `no-new-privileges`. PostgreSQL and application services have no LAN port mapping.
- Caddy state is persistent because it contains the internal CA. It is included in encrypted daily backups and must be treated as sensitive.

## Configuration and secrets

`server/.env.production.example` is the authoritative template. `Initialize-Production.ps1` generates `server/.env.production`, and Git ignores it. The file contains database and backup secrets and is ACL-restricted. Do not email it or place it on an unencrypted share.

The Restic repository is encrypted, but disaster recovery still requires the Restic password to unlock it. Keep that password and a copy of the production environment in an independent recovery channel: a clinic password vault plus a sealed, BitLocker-encrypted recovery USB is recommended.

## Remaining site decisions

- Confirm the actual static IP, subnet, and hostname.
- Confirm Docker Desktop licensing and Windows edition.
- Confirm the backup disk is physically separate and BitLocker-protected.
- Decide who receives Windows Event Log alerts and checks them daily.
- Review retention against local medical-record and privacy requirements.
- Have the physician validate work-leave wording and every clinical template.
- Perform target-PC, LAN, UPS, power-loss, multi-user, printer, and restore acceptance tests before declaring deployment complete.
